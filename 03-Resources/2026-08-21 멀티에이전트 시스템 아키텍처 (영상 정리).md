유튜브 "Multi-agent Systems Explained in 17 Minutes" 시청 정리(2026-08-21, `watch` 스킬 transcript 모드). [[AI 협업 운영 규칙]]에서 Claude–Codex 작업 분담 규칙의 근거로 인용됨.

## 1. 작업을 나눌지 말지 — 분해 가능성이 기준

에이전트를 여러 개로 나누는 게 항상 좋은 게 아니다. 기준은 작업이 **분해 가능한가(decomposable)**인지다.

- **순차적 작업**: 앞 단계 결과가 다음 단계 입력으로 바로 쓰이는 작업. 예: 분류기 출력을 GUI에 새로 연결하는 통합 작업. 이런 작업을 억지로 나누면 에이전트마다 서로 다른 가정을 하게 되고, 조정 비용만 늘고 버그가 생기기 쉽다 → **한 에이전트가 끝까지 진행**.
- **분해 가능한 작업**: 서로 참조하지 않는 독립적인 하위작업. 예: GUI 파일과 분류기 파일이 지금 당장 서로 안 겹치는 경우 → 나눠서 병렬 진행 가능.

**Google의 45% 휴리스틱**: (영상에서 인용된) 실무 경험칙 — 작업의 약 45% 정도가 실제로 유의미하게 분해 가능한 성격을 갖는다는 관찰. 즉 대부분의 작업은 나누기보다 한 에이전트가 처리하는 편이 낫다는 시사점.

## 2. 4가지 멀티에이전트 아키텍처와 에러 증폭

| 아키텍처 | 특징 | 에러 증폭 |
|---|---|---|
| 독립형(Independent) | 에이전트들이 서로 대화 없이 각자 병렬로 작업 | **가장 나쁨 — 같은 연구에서 에러 17배 증가로 보고됨** |
| 분산형(Decentralized) | 에이전트끼리 직접 소통하되 중앙 조정자 없음 | 중간 |
| 중앙집중형(Centralized) | 중앙(사용자 또는 오케스트레이터)이 작업을 배정하고 결과를 검토·통합 | **가장 낮은 에러 증폭** |
| 하이브리드(Hybrid) | 중앙 조정 + 부분적 에이전트 간 직접 소통 | 상황에 따라 |

현재 Claude–Codex 협업 구조(사용자가 작업을 배정하고 결과를 검토하는 방식, 이후 agentmemory 메일함으로 일부 직접 소통 추가)는 **중앙집중형에 하이브리드 요소가 섞인 구조**에 해당한다.

## 3. 비용은 선형이 아니라 초선형(super-linear)으로 증가

에이전트 수를 늘릴수록 조정(coordination) 오버헤드 때문에 비용이 에이전트 수에 비례하는 것 이상으로 늘어난다. 2026-08-20 세션 하나가 서브에이전트를 사용해 $114.37(13개 세션 총비용의 91%)을 소모하며 컨텍스트도 93.4%까지 찍은 사례가 이 원리를 실측으로 보여줬다.

## 실무 시사점 (이 vault/프로젝트에 적용)
- 습관적으로 작업을 나누지 않는다 — 나눌 가치가 있는지(분해 가능성) 먼저 판단한다.
- 나눌 때도 서로 겹치지 않는 파일·기능 단위로만 나눈다(동시 편집 금지).
- 여러 서브에이전트를 병렬로 굴리는 방식은 비용·에러 양쪽에서 리스크가 크므로, 서브에이전트 사용 전 사용자 확인을 거치기로 함(별도 규칙, `confirm-before-subagents` 메모리).
