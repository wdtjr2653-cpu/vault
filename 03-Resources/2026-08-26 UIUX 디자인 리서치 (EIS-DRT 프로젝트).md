## 사이클 1 (2026-08-26)

### 1. 경쟁 제품 대시보드 — TWAICE 배터리 분석 플랫폼
- 업계 선두 [TWAICE 플랫폼](https://www.twaice.com/products/platform)의 정보 구조: **Configuration(계정·이벤트·알림·리포트) / Battery(RUL 시뮬레이터·프로파일 분석) / Monitoring(데이터 탐색기·상관 탐색기) / Analytics(건강도·성능·이상 감지)** 4계층 — UI와 API 병행 제공
- 안전 모니터링은 내부저항·온도 추이·불균형 KPI를 상시 감시하고 **이슈를 high/medium/low 심각도로 자동 분류** — 우리 "정상/주의/불량" 3단계와 동일한 관행. [안전 모니터링 페이지](https://www.twaice.com/products/energy-storage-analytics/safety)
- **시사점**: 우리 콘솔에 아직 없는 것 = ① 알림/이벤트 이력 뷰 ② 상관 탐색기(온도↔저항 등 변수 간 상관) ③ 포트폴리오(배치 전체) 뷰 — 다음 화면 확장 후보. "배치 요약" 카드가 그 씨앗
- AVILOO는 장비(BOX)+리포트 중심, TWAICE는 클라우드 플랫폼 중심 — 우리 포지션(이동형 장비+현장 콘솔)은 그 중간이라 **현장 1화면 완결성**이 차별화 포인트

### 2. 데이터 밀집 대시보드 원칙 (2025-26 통용)
- [UXPin 대시보드 원칙](https://www.uxpin.com/studio/blog/dashboard-design-principles/) 등 공통 결론:
  - **역할별 최우선 KPI 1~3개에 시각 계층 집중** — 나머지는 드릴다운. 우리 화면의 "판정 배지 > 신뢰도 > 세부 수치" 계층과 일치
  - **색 의미의 일관성**: Grafana처럼 같은 대상에 항상 같은 색 → 사용자의 멘탈 모델 형성 ([Toptal 사례](https://www.toptal.com/designers/data-visualization/dashboard-design-best-practices)) — 우리 "그룹=색상, 개체=진하기(R_ohm)" 규칙이 정확히 이 방향
  - 신호등(녹/황/적) 체계는 Datadog·New Relic 등 엔지니어링 도구 표준 — 단 색약 대응 필요(아래)
  - 대용량 렌더링: lazy loading·페이지네이션 — 30개+ 오버레이의 밴드 요약 방식이 같은 문제의식
- **시사점**: 현재 시안이 업계 원칙과 잘 정렬됨. 남은 격차는 "사용 데이터 기반 반복 개선"(히트맵·미사용 위젯 제거) — 구현 후 과제

### 3. 색약 접근성 — 현 색 체계의 리스크와 보완
- [색약 대시보드 가이드](https://medium.com/@courtneyjordan/designing-color-blind-accessible-dashboards-ba3e0084be82) 공통 지적: **적록색약(전체 남성 ~8%)에게 레드/앰버 계열은 구분이 어려움** — 우리 주의(앰버) vs 불량(레드)이 정확히 위험 쌍
- 업계 권장: ① 색 외 보조 채널(아이콘·라벨·패턴) 병행 ② [Okabe-Ito 8색](https://colorblind.io/guides/colorblind-safe-palettes) 같은 검증 팔레트 ③ 블루 계열은 대부분의 색각이상에 안전 — 정상=인디고 선택은 우연히도 최적
- **시사점 (시안 반영 후보)**: 상태 점·배지에 색+모양 이중화 — 정상 ●, 주의 ▲, 불량 ✕ 처럼 형태 차이 추가. 파일 목록·범례·차트 마커에 일괄 적용하면 색약 사용자도 완전 판독 가능. 심사 시 접근성 어필 포인트도 됨

## 사이클 2 (2026-08-26 17:28) — 계측·과학 SW 차트 인터랙션

### 1. 과학 시각화 인터랙션 표준 패턴
- 시각 탐색의 고전 원칙 = Shneiderman의 **"Overview first, zoom & filter, details-on-demand"** ([시계열 시각화 리뷰](https://arxiv.org/html/2507.14920v1)) — 전체 개요 → 브러시로 관심 구간 선택 → 상세 뷰. 우리 콘솔은 "배치 요약 → 파일 선택 → 개별 진단"으로 이미 이 구조를 따름
- **연동 브러싱(linked brushing)**: 한 차트에서 구간·점을 선택하면 연결된 다른 뷰에서 같은 대상이 하이라이트 ([Observable 사례](https://observablehq.com/blog/linked-brushing)) — 줌·팬도 뷰 간 동기화가 표준
- **시사점 (액션 후보)**: Nyquist ↔ DRT **양방향 연동 브러싱** — Nyquist에서 주파수 구간을 드래그하면 DRT의 대응 τ 구간이 하이라이트(τ=1/2πf 매핑), 반대도 동일. 두 차트가 "같은 데이터의 두 얼굴"임을 인터랙션으로 증명하는 기능이라 시연 효과 큼. 판정 근거↔피크 연동의 확장판

### 2. 오실로스코프 UI의 커서 측정 관행
- 계측기 표준: **듀얼 커서** — 파형 위 세로/가로 마커 2개를 드래그해 두 지점의 값과 **차이값(ΔV, ΔX)을 상시 리드아웃**으로 표시 ([EDN 커서 해설](https://www.edn.com/oscilloscope-cursors-complement-other-measurement-tools/), [Tektronix 5 Series UI](https://www.tek.com/en/blog/inside-5-series-mso-re-inventing-oscilloscope-user-interface))
- 리드아웃은 플롯 모서리에 고정 표시, 측정 결과는 우측 결과 바에 블록으로 축적 — Teledyne LeCroy MAUI도 동일 패턴
- **시사점 (액션 후보)**: Nyquist·DRT에 **Δ커서 모드** 추가 — 커서 2개를 놓으면 ΔZ′(mΩ), Δτ(decade), Δγ 차이값이 리드아웃으로 표시. "이 셀과 기준의 R_ct 차이가 정확히 몇 mΩ인가"를 화면에서 바로 재는 기능 = 계측 장비 사용자(정비사·엔지니어)에게 익숙한 문법이라 학습 비용 없음

- [ ] 듀얼 Δ커서 측정 모드 + 모서리 리드아웃

## 사이클 3 (2026-08-26 18:00) — 진단 리포트(PDF) 디자인

### 1. 차량·배터리 점검 리포트 구조 관행
- 업계 표준 구조([배터리 점검 리포트 템플릿](https://oxmaint.com/industries/fleet-management/battery-inspection-guide), [SafetyCulture 차량 점검](https://safetyculture.com/checklists/safety/vehicle-inspection)): **① 식별정보(차량/배터리·일시·검사자) → ② 항목별 판정(Pass/Fail/N/A 체크) → ③ 측정값 기록 → ④ 관찰·코멘트 자유기입 → ⑤ 서명/승인**
- 현장용은 인쇄 전제(print-ready PDF) + 웹링크 공유 병행이 표준
- **시사점**: 우리 "진단 리포트 내보내기"의 목차 초안 = ① 셀·측정 식별(파일명·장비·세션·온도) ② 종합 판정 배지+신뢰도 ③ 수치 테이블(R_ohm·R_ct·SoH, 기준 대비 편차) ④ Nyquist·DRT 차트(라이트 테마 필수 — 인쇄용) ⑤ 판정 근거 기여도 ⑥ 수치 신뢰도(KK·식별가능성) ⑦ 면책 문구·검사자 서명란. **⑥·⑦은 경쟁 리포트에 없는 차별 요소**(AVILOO 인증서 대비 투명성 우위)

### 2. 인쇄물 타이포·차트 가독성 기준
- 본문 10–12pt, 최소 6pt(인쇄)/9pt(화면), 좌측 정렬, 고대비 저채도 본문 ([데이터 시각화 타이포 표준](https://xdgov.github.io/data-design-standards/components/typography), [Urban Institute 스타일가이드](https://urbaninstitute.github.io/graphics-styleguide/))

### 1. Electron vs Tauri (2026 기준)
- [비교 자료들](https://blog.openreplay.com/comparing-electron-tauri-desktop-applications/) 공통 결론: **Tauri가 신규 프로젝트의 기술적 우위** — 메모리 58~75%↓(유휴 ~180MB vs ~45MB), 설치본 ~165MB vs ~8MB, 콜드 스타트 3.2s vs 1.4s. Electron 강점은 프런트팀의 출시 속도·생태계 성숙도
- Tauri는 OS 내장 WebView 사용(Chromium 미동봉) — 백엔드가 Rust지만 **사이드카로 파이썬 프로세스 실행 가능**
- **시사점**: Claude Design이 뽑아준 React/HTML 코드를 그대로 쓰는 경로라면 **Tauri(웹 프런트 + drt_analysis 파이썬 사이드카)**가 현장 배포(가벼운 설치본, 낮은 사양 PC)에 유리. Electron은 개발 편의 우선일 때
- 현장 진단 장비에 얹는 시나리오면 설치 용량·메모리가 실제 제약이 됨 — Tauri 우세

### 2. PyQt/PySide 경로 (기존 GUI 개조)
- [PythonGUIs 2026 가이드](https://www.pythonguis.com/faq/which-python-gui-library/): PyQt/PySide는 여전히 과학·계측 데스크톱의 최강 툴킷 — 하드웨어 연동·데이터 시각화 직결이 강점

  - **A안 (웹 프런트 + Tauri)**: Claude Design 코드 재사용 ↑, 디자인 충실도 100%, 파이썬은 사이드카/로컬 API — 신규 개발이지만 시안이 곧 코드라 실질 비용 낮음
  - **B안 (기존 PyQt 개조)**: 기존 GUI 자산 재사용 ↑, 하드웨어 연동 코드 그대로 — 대신 디자인 시안은 "사양서"로만 쓰이고 QSS 재구현 비용 발생

- **시사점**: 지금까지 확정한 색 규칙 전부(인디고 램프 라이트/다크 시프트, 불량 레드, OKLCH 보간, R_ohm 매핑)를 **토큰 파일 하나로 코드화**하면 시안↔구현 간 색 불일치가 원천 차단됨. 우리가 이미 겪은 "다크에서 묻히는 문제"가 시맨틱 층에서 한 번에 관리됨

### 2. 차트 색 토큰의 분류
- 관행([Cloudscape 데이터 시각화 색](https://cloudscape.design/foundation/visual-foundation/data-vis-colors/) 등): 차트 색은 UI 색과 분리된 전용 그룹으로, **categorical(범주)/sequential(순차)/semantic(의미)** 유형별 토큰화
- **시사점**: 우리 차트 색의 정확한 분류 = **semantic(그룹: 정상/주의/불량) × sequential(그룹 내 R_ohm 순차)** 2차원 — 토큰 명명 제안: `--trace-normal-{1..4}`, `--trace-warning-{1..3}`, `--trace-fault-{1..3}`, `--trace-reference`, `--band-normal-fill`. 이 이름 체계는 엔진 JSON의 그룹 필드와 1:1로 붙어 프런트 구현이 단순해짐

### 1. 응답 시간 3임계값

- 스몰 멀티플: 측정 회차별 개별 패널을 만화 컷처럼 좌→우 배열 — 회차 간 비교엔 최강이나 미세 변화 추적엔 약함
- 정비 분야 공통 패턴: **전역 지표 트렌드(스칼라 vs 시간) + 스펙트럼 진화(형태 vs 시간) 2계층 병행** — 트렌드로 "언제부터 나빠졌나", 스펙트럼으로 "무엇이 나빠졌나"

### 2. 우리 이력 뷰 설계 시사점
- **2계층 구성이 정답**: ① 상단 = 특징값 추이 차트(R_ohm·R_ct·R_diff vs 측정일 — 피크 면적=저항이므로 DRT 피크별 궤적이 그대로 열화 스토리) ② 하단 = 스펙트럼 진화(기존 Nyquist/DRT 오버레이 재사용 + **시간 컬러램프**). 3D 워터폴은 비채택(가림+비용, 컬러램프 오버레이가 동일 정보 전달)
- **색 규칙 충돌 주의**: 배치 뷰에선 "진하기=R_ohm 크기"인데 이력 뷰에선 **"진하기=시간 순(옛것 연하게→최신 진하게)"으로 의미 전환** — 같은 인디고 램프를 쓰되 컬러바 라벨을 "측정일"로 명시, 뷰 전환 시 혼동 방지 필요
- **DRT 피크 궤적**: 피크 위치(τ)·면적(R)을 회차 간 연결선으로 추적 — "P2(R_ct)가 3회차부터 급증" 같은 서사가 판정 근거(XAI, C32)와 직결
- **엔진 제약**: 현재 JSON 계약에 measured_at 없음(합의 사양) — 이력 뷰는 파일명 타임스탬프 파싱 또는 meta 확장 필요. **vault-36과 협의 항목**. 그 전까지는 "이력 데이터 준비 중" placeholder 원칙(C7) 적용

## 사이클 39 (2026-08-31) — 단위·수치 표기 규칙 (유효숫자·정렬·SI)

### 1. 표 안의 숫자 타이포 규칙
- 표준([Design Better Data Tables](https://medium.com/mission-log/design-better-data-tables-430a30a00d8c), [A List Apart 표 타이포](https://alistapart.com/article/web-typography-tables/), [tabular-nums](https://theosoti.com/short/tabular-nums/)): ① **tabular numerals**(고정폭 숫자)로 세로 정렬 — CSS `font-variant-numeric: tabular-nums` 한 줄 ② 수치 열은 **우측 정렬**(자릿수 다르면 소수점 정렬), 가운데 정렬 금지 ③ **열 내 소수 자리 통일** — 같은 열에서 18.2와 18.25가 섞이면 비교 불가, 1~2자리가 일반 규칙
- **시사점**: 숫자 폰트로 IBM Plex Mono를 이미 확정(모노스페이스라 tabular 문제 자동 해결) — 남은 건 **자리수 규칙 명문화**: R값(R_ohm·R_ct·R_diff)은 mΩ 소수 1자리(18.2 mΩ), 신뢰도 % 소수 1자리, 온도 정수. 측정 원자료의 초과 정밀도(18.2473…)는 툴팁·리포트 상세에서만

### 2. SI 표기 규칙 (NIST SP 811) — 계측 도구의 신뢰 디테일
- 공식 규칙([NIST SI 작성 가이드](https://www.nist.gov/pml/owm/writing-si-metric-system-units), [SP 811 7장](https://nist.gov/pml/special-publication-811/nist-guide-si-chapter-7-rules-and-style-conventions-expressing-values)): **숫자와 단위 기호 사이 공백 필수** — "18.2 mΩ", "25 °C"(°C도 공백, 예외는 각도 °′″뿐). 단위 기호는 정체(기울임 금지), 복수형 없음
- **시사점** (틀리면 전문가 사용자에게 바로 들키는 부분): ① 앱 전역 **mΩ 고정**(엔진 Ω→프런트 변환, 합의 사양) — 축·툴팁·카드·리포트 표기 통일 ② 주파수는 **접두어 자동 전환**(10 kHz / 1 Hz / 32 mHz — "10000 Hz" 금지) ③ 지수 표기는 **λ에만 허용**(1.2×10⁻³, 고급 정보 영역) — 일반 화면에서 지수 표기는 검사원에게 부담 ④ τ 축의 10ⁿ 라벨은 유지(로그 축 관행)
- 이 규칙 전부가 **디자인 토큰(C22)과 같은 층위의 "수치 표기 토큰"** — 구현 시 포맷 함수 하나(`formatR()`, `formatFreq()`)로 중앙화하면 화면·리포트·내보내기 CSV가 자동 일관

### 사이클 39 액션 후보
- [ ] 수치 표기 규칙표 확정: R값 mΩ 소수 1자리 / 신뢰도 % 1자리 / 온도 정수 / 열 내 자리 통일·우측 정렬·tabular
- [ ] SI 표기 준수: 숫자-단위 공백("18.2 mΩ", "25 °C"), 주파수 접두어 자동 전환, 지수 표기는 λ 한정
- [ ] (구현) 포맷 함수 중앙화 (formatR/formatFreq 등) — 화면·리포트·CSV 내보내기 표기 단일 소스

## 사이클 40 (2026-08-31) — 차트 툴팁·호버 리드아웃 (다중 곡선에서 값 읽기)

### 1. 트리거 방식 2종과 선택 기준
- 라이브러리 공통 문법([ApexCharts tooltip](https://apexcharts.com/docs/options/tooltip/), [amCharts cursor](https://www.amcharts.com/docs/v5/concepts/common-elements/tooltips/), [ZingChart 크로스헤어](https://blog.zingsoft.com/tooltips-and-crosshairs-for-interactive-graphs/)): **axis 트리거**(크로스헤어 + 같은 x의 전 시리즈 값 공유 툴팁) vs **item 트리거**(최근접 포인트 1개). 공유 툴팁은 전 시리즈가 같은 x 격자를 공유할 때만 성립. 호버 시 **해당 곡선 강조 + 나머지 감쇄(gray-out)**가 다중 시리즈 표준
- **시사점 — 차트별로 트리거가 달라야 함**: ① **Nyquist는 매개변수 곡선이라 axis 트리거 자체가 성립 불가**(x가 독립변수가 아님 — 같은 Z'에 두 주파수가 대응 가능) → **최근접 포인트(item) 트리거 + 곡선 강조/감쇄**가 유일해 ② **DRT·Bode는 로그 x축 공유** → 크로스헤어 + 공유 툴팁 가능. 단 30개 오버레이에서 30행 툴팁은 불가 — **5개 이하면 전체 나열, 초과 시 호버 곡선+기준선만** 표시
- 툴팁 내용 규칙: 셀ID(색 도트 병기) + **주파수 f 필수 포함**(Nyquist에서 f는 화면에 안 보이는 숨은 축 — "18.2 mΩ, -4.1 mΩ @ 32 Hz") — 수치 포맷은 C39 포맷 함수 재사용

### 2. 커서 추적 툴팁 vs 고정 리드아웃 병행
- 관행: 짧은 값은 커서 따라다니는 툴팁, 정밀 판독은 **모서리 고정 리드아웃**(오실로스코프 문법, C2와 일치) — 둘은 대체가 아니라 병행. 크로스헤어의 축 라벨(축 위 현재값 배지)이 판독 정밀도를 올림
- **시사점**: 우리 확정 사항들이 자연 결합 — 기본 호버는 가벼운 툴팁(셀ID+2~3값), **Δ커서 측정 모드(C2 구현 항목) 진입 시엔 툴팁을 끄고 모서리 리드아웃으로 전환**(두 UI가 겹치면 혼란). Nyquist↔DRT 연동 브러싱(C2)과도 연결: Nyquist에서 f 호버 → DRT의 τ=1/(2πf) 위치에 세로 가이드 동기 표시
- **터치(현장 태블릿, C5) 대응**: hover가 없으므로 **탭 = 최근접 포인트 고정 선택**(다시 탭하면 해제) — 고정된 리드아웃 카드로 표시, 손가락에 가려지지 않게 포인트 위쪽 오프셋

### 사이클 40 액션 후보
- [ ] Nyquist 툴팁 = item 트리거(최근접 포인트) + 곡선 강조/타곡선 감쇄 + f 병기 리드아웃 — axis 트리거 금지 명문화
- [ ] DRT·Bode 툴팁 = 크로스헤어 공유형, 5개 초과 오버레이 시 호버+기준만 표시
- [ ] Δ커서 모드 진입 시 툴팁→모서리 리드아웃 전환 (이중 표시 금지)
- [ ] 터치 탭 고정 선택 (호버 대체) — 현장 태블릿 시나리오

## 사이클 41 (2026-08-31) — 차트 이미지·데이터 클립보드 복사 (경량 내보내기)

### 1. 복사 경로의 관행과 기술 제약
- 관행([web.dev 클립보드 이미지](https://web.dev/patterns/clipboard/copy-images/), [Figma Copy as SVG](https://help.figma.com/hc/en-us/articles/360040030374-Copy-assets-between-design-tools), Miro·Excalidraw류): 화이트보드·차트 도구에서 "이미지로 복사"는 가장 사랑받는 경량 공유 경로 — 클립보드 API는 **PNG 바이너리 복사 지원, SVG는 소스 텍스트로만** 복사 가능. 대시보드 도구들은 이미지(PNG/SVG/PDF)와 데이터(CSV/Excel) 내보내기를 별도 축으로 제공
- **시사점**: 검사원의 실제 고빈도 시나리오는 리포트 PDF(C16)가 아니라 **"메일·메신저에 차트 한 장 붙여넣기"와 "엑셀에 수치 붙여넣기"** — 차트 카드 우상단 ⋯ 메뉴(또는 우클릭)에 3종: ① 이미지 복사(PNG) ② 이미지 저장(PNG/SVG — SVG는 보고서 편집용) ③ 데이터 복사(표). C16 내보내기 대화상자와 별개의 **원클릭 경량 경로**로 유지

### 2. 복사 산출물의 품질 규칙 (스크린샷과의 차별점)
- **테마 강제**: 다크 모드에서 복사해도 **복사 이미지는 항상 라이트 테마+흰 배경으로 재렌더** — 메일·워드 문서의 흰 배경에서 다크 차트는 이질적이고 잉크도 낭비(C3 흑백 인쇄 원칙과 동일 축). 해상도는 2x(레티나·문서 확대 대비)
- **맥락 스탬프**: 복사 이미지 하단에 작은 풋터 자동 삽입 — "CELL-B12 · 2026-08-31 14:02 · 판정 불량 · DRT-NET v2.4" — 맥락 잃은 스크린샷이 보고 체인을 떠도는 것 방지, 모델 버전 감사(C27)·인증서 신뢰 축과 일치. 이것이 OS 스크린샷 대비 "앱이 제공하는 복사"의 존재 이유
- **데이터 복사는 원 정밀도**: 표시용 반올림(C39, mΩ 1자리)은 화면·이미지에만 — 클립보드 데이터는 **TSV(엑셀 붙여넣기 호환) + 원 정밀도 + 헤더에 단위 명기** — 검사원이 엑셀에서 재계산할 때 반올림 누적 오차 방지

### 사이클 41 액션 후보
- [ ] 차트 카드 ⋯/우클릭 메뉴 3종: 이미지 복사(PNG) / 이미지 저장(PNG·SVG) / 데이터 복사(TSV) — C16과 별개 원클릭 경로
- [ ] 복사 이미지 = 항상 라이트 테마·흰 배경·2x + 셀ID·시각·판정·모델버전 풋터 스탬프
- [ ] 데이터 복사 = 원 정밀도 TSV + 단위 헤더 (표시 반올림은 화면·이미지 한정)

## 사이클 42 (2026-08-31) — 데스크톱 앱 자동 업데이트·버전 관리 UX

### 1. 업데이트 적용 방식의 표준 패턴
- 관행([Chrome·Slack·VS Code 3패턴 분석](https://codenote.net/en/posts/windows-desktop-app-per-machine-silent-auto-update-patterns/), [ownCloud 자동 업데이트](https://doc.owncloud.com/desktop/next/automatic_updater.html)): 주류는 **백그라운드 다운로드 + 다음 실행 시 조용히 적용**(Chrome은 앱이 꺼져 있을 때 작업 스케줄러로 체크) — 사용 중 강제 재시작은 최악의 UX. 긴급 수정만 즉시 적용(IMMEDIATE), 나머지는 유예. 엔터프라이즈는 채널(안정/베타)·**버전 고정(pinning)**·단계적 롤아웃 정책 제공이 표준
- **시사점**: 우리 도구엔 절대 규칙이 하나 추가됨 — **측정·DRT 변환 진행 중에는 재시작 유도 UI 자체를 억제**(라이브 측정 1시간짜리 스윕 도중 "재시작하세요" 배너는 사고). 업데이트 알림은 알림 센터(C13)로만, 적용은 다음 실행 시

### 2. 진단 도구 특유의 2축 버전 관리 + 폐쇄망 배포
- **앱 버전 ≠ 모델 버전**: 판정 모델(DRT-NET) 변경이 포함된 업데이트는 일반 업데이트와 다르게 취급 — C27 규칙(명시적 배너 "판정이 달라질 수 있습니다") 연동. 모델 변경 없는 UI 업데이트는 조용히. 정보 화면·리포트에 **앱 버전+모델 버전 병기**
- **거래기관·폐쇄망 현실**([엔터프라이즈 관리 사례](https://amitkoth.com/claude-desktop-update-management-enterprise/)): 관리 PC는 쓰기 권한·네트워크 제한으로 자동 업데이트가 자주 실패 → **버전 드리프트**(기관마다 다른 버전) 발생. 대응: ① 오프라인 인스톨러 제공(USB/내부망 배포) ② 기관용 버전 고정 옵션 ③ 드리프트는 리포트의 버전 병기로 감사 가능 — "어느 버전으로 발급된 인증서인가"가 항상 문서에 남으므로 분쟁 방어(C27·C31)와 일관
- **시사점**: 실증 단계에서 기관마다 업데이트 정책이 다를 것 — 설정 [정보]에 업데이트 채널·현재 버전·모델 버전·"업데이트 확인" 수동 버튼을 모아 관리자가 통제 가능하게

### 사이클 42 액션 후보

- [ ] 폐쇄망 배포 대비: 오프라인 인스톨러 + 기관용 버전 고정 옵션 + 리포트에 앱·모델 버전 병기
- [ ] 설정 [정보]: 채널·버전 2축·수동 업데이트 확인 버튼 집약

## 사이클 43 (2026-08-31) — 로그인·권한 UX (역할별 화면 차등)

### 1. Hide vs Disable — 권한 UI의 기본 문법
- 원칙([Smashing — Hidden vs Disabled](https://www.smashingmagazine.com/2024/05/hidden-vs-disabled-ux/), [Helios 디자인 시스템 패턴](https://helios.hashicorp.design/patterns/disabled-patterns)): **그 역할이 영원히 쓸 수 없는 기능은 숨기고**(발견성 손해보다 혼란 제거 우선 — 관리자 전용 설정 등), **조건 충족 시 쓸 수 있는 기능은 비활성+사유 툴팁**("승인 권한이 없습니다 — 책임자 계정 필요"). 설명 없는 회색 버튼이 최악
- 권한 화면 설계([Budibase RBAC 가이드](https://budibase.com/blog/app-building/role-based-access-control/)): 저수준 권한 나열 대신 **역할 요약형**("검사원은 진단·리포트, 책임자는 승인, 관리자는 설정") — 인지 부하를 낮추고 투명성 유지

### 2. 우리 도구의 단계적 권한 모델
- **기본은 로그인 없음**: 초기(사내 단독 사용)에 로그인 화면은 순수 마찰 — YAGNI. 권한 개념이 실제로 필요해지는 트리거는 실증 단계의 두 기능: 2단계 승인(C33)·판정 재정 override(C32) — **"승인 워크플로 활성화" 스위치를 켜는 순간 로그인이 필수가 되는 구조**(행위자 없는 승인은 감사 불가라 논리적 필연)
- **역할 3종 최소셋**: ① 검사원 — 측정·진단·리포트 발급 ② 책임자 — +승인·재정 검토 ③ 관리자 — +설정(판정 영향 가드레일 C14)·업데이트 채널(C42)·기관 정책. 이 이상 세분화는 실증 요구 나올 때까지 보류
- **행위자 기록의 연쇄**: 로그인 도입 시 감사 로그(C13)·리포트 서명란·셀 메모(C33)·override 기록(C32)에 **사용자명 자동 병기** — 오프라인 데스크톱이므로 로컬 계정+PIN 수준의 가벼운 인증이면 충분(외부 IdP는 기관 요구 시)
- **화면 차등 적용**: 검사원 화면에서 관리자 설정 탭은 숨김, 승인 버튼은 비활성+사유 툴팁(위 문법 그대로) — 커맨드 팔레트(C9)·설정 검색에서도 권한 밖 항목은 미노출로 일관

### 사이클 43 액션 후보
- [ ] 단계적 권한 모델: 기본 로그인 없음 → 승인 워크플로 활성화 시 로그인 필수 (로컬 계정+PIN)
- [ ] 역할 3종(검사원/책임자/관리자) 요약형 권한 화면 — 저수준 권한 나열 비채택
- [ ] hide/disable 규칙 명문화: 영구 불가=숨김, 조건부=비활성+사유 툴팁 (팔레트·검색도 일관)
- [ ] 로그인 시 행위자 자동 병기: 감사 로그·리포트 서명란·메모·override 기록
