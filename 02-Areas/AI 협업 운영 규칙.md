#area/ai-collaboration

## 개요
사용자는 Claude와 ChatGPT/Codex를 하나의 공동 작업 체계로 사용한다. 이 문서는 두 에이전트가 회사 PC(`LJS2653`)와 집 PC를 오가며 작업할 때 지켜야 할 공통 운영 규칙의 **기준 문서**다.

## 에이전트별 기본 역할
| 에이전트 | 우선 활용 영역 |
|---|---|
| Claude | Gmail·Drive 확인, 기존 맥락 파악, 문서 초안 작성, Obsidian 정리 |
| Codex | 코드 구현, 데이터 처리, 테스트·검증, Git 변경 관리 |

역할은 고정된 독점 영역이 아니라 작업 성격에 따라 조정 가능하다.

### 문서작성·리서치·브라우저·시각화 — 담당 정하는 기준 (2026-08-21 정정)
처음엔 "이 영역은 Claude만 가능"이라고 적었는데 **부정확했다** — Codex의 `~/.codex/config.toml`을 실제로 확인해보니 `documents`/`pdf`/`spreadsheets`/`presentations`(Word·PDF·Excel·PPTX 생성) 플러그인과 `browser`(브라우저 자동화)·`visualize`(데이터 시각화) 플러그인이 전부 기본 번들로 들어있었다. **Claude와 Codex 둘 다 문서 작성·웹 리서치·브라우저 자동화·데이터 시각화가 가능**하다.

**포맷별 실제 확인(2026-08-21)**: 워드(.docx)·엑셀(.xlsx)·파워포인트(.pptx)·PDF는 Codex도 OpenAI 자체 OOXML 플러그인 + Claude와 동일한 `document-skills`(docx/xlsx/pptx/pdf 스킬 파일까지 동일)를 둘 다 갖고 있어 완전히 대등하다. 반면 **한글(HWP)은 Claude·Codex 어느 쪽에도 공식 스킬이 없다** — Claude도 `pyhwp`를 직접 설치해 우회하는 방식이고, 이건 특권이 아니라 둘 다 없는 기능이다(같은 PC라 pyhwp가 이미 설치돼 있으니 Codex도 같은 방식 사용 가능).

그래서 담당은 "누가 그 능력을 갖고 있냐"가 아니라 아래 기준으로 정한다:
- **실제로 연결된 도구·로그인 세션이 있는가** — 예: Gmail/Drive는 이 환경에서 Claude 세션에만 연결돼 있고(`ljs2653@monaelec.com` OAuth), Codex config엔 Gmail/Drive MCP가 없음(2026-08-21 확인). 이런 서비스별 작업은 실제 커넥터가 붙어있는 쪽에 배정한다.
- **작업 특성** — 예: 코드/데이터 파이프라인과 엮인 시각화는 Codex, Drive·Obsidian 등 문서/맥락과 엮인 작업은 Claude가 자연스러울 수 있음(고정 규칙 아님).
- **결과 품질** — 실제로 해보고 더 나은 쪽으로 조정 가능. 역할표는 시작점일 뿐 절대 규칙이 아니다.

특정 서비스(Gmail/Drive/Calendar 등)에 작업을 배정하기 전엔 **해당 에이전트에 그 서비스의 커넥터가 실제로 연결돼 있는지부터 확인**할 것 — 없으면 작업 자체가 불가능하다.

## 이 문서는 언제 확인하나 (매 작업 전 아님 — 조건부)
다음 경우에만 이 문서를 읽는다:
- Claude와 Codex에 작업을 분담할 때
- 다른 에이전트의 결과를 인계받거나 검토할 때
- 회사와 집 환경을 이동한 뒤 작업을 이어갈 때
- 동일 파일 또는 동일 Git 저장소에서 충돌 가능성이 있을 때
- 담당 에이전트나 저장소의 기준이 불분명할 때

단순 질문, 독립적인 새 작업, 짧고 자기완결적인 작업에서는 이 문서를 불필요하게 읽지 않는다. (그 경우에도 "나눌 가치가 있는 작업인가"만 스스로 판단 — 아래 기준 참고)

## agentmemory는 언제 우선 검색하나 (매번 아님 — 조건부)
- 사용자가 이전 작업을 이어달라고 할 때
- DRT 등 기존 프로젝트를 계속 작업할 때
- 과거 결정, 사용자 선호, 시행착오가 필요한 작업일 때
- 현재 파일이나 기능의 변경 이유를 확인해야 할 때
- 다른 에이전트의 작업을 인계받을 때

새롭고 독립적이며 과거 맥락이 필요 없는 작업에서는 자동으로 검색하지 않는다.

## 나눌지 말지 판단 기준 (2026-08-21, "Multi-agent Systems Explained" 영상 반영)
- **순차적 작업**(앞 단계 결과가 다음 단계에 바로 필요한 작업, 예: 분류기 출력을 GUI에 새로 연결하는 통합 작업)은 **나누지 않고 한 에이전트가 끝까지 진행**한다. 나누면 조정 비용만 늘고 서로의 가정이 어긋나 버그가 생기기 쉽다.
- **분해 가능한 작업**(서로 안 겹치는 파일·독립적인 하위작업, 예: GUI 파일 vs 분류기 파일처럼 지금 당장은 서로 참조하지 않는 작업)만 나눈다.
- 지금 구조(사용자가 작업을 배정하고 검토하는 방식)는 영상의 "중앙집중형" 아키텍처에 해당 — 4개 아키텍처 중 에러 증폭이 가장 낮다고 보고됨. 서로 대화 없이 그냥 병렬로만 돌리는 "독립형"은 같은 연구에서 에러가 17배 늘었다고 보고됨 — 그래서 "동시 편집 방지" 원칙을 반드시 지킨다.
- 비용 관점: 에이전트를 늘릴수록 조정 오버헤드 때문에 비용이 선형이 아니라 그 이상으로 늘어난다(예: 오늘 발견한 $114 세션). 굳이 안 나눠도 될 작업까지 습관적으로 나누지 않는다.

## 회사·집 환경 구분
- 컴퓨터명 `LJS2653` = 회사 PC
- 그 외 컴퓨터 = 집 PC

### 세 저장소의 실제 공유 범위 (2026-08-21 실측 확인)
"각각 로컬이라 안 겹친다"가 아니라, **범위가 서로 다르다**:
| 저장소 | 같은 PC 안(Claude↔Codex) | 다른 PC(회사↔집) |
|---|---|---|
| **agentmemory** | ✅ 실시간 공유 — 같은 로컬 서버(`127.0.0.1:3111`)에 둘 다 접속함(`~/.codex/config.toml`의 `mcp_servers.agentmemory`로 확인) | ❌ PC마다 별도 서버·DB, 동기화 안 됨 |
| **Obsidian(`C:\vault`)** | ✅ 같은 폴더를 파일로 직접 읽고 씀 | ⏳ Git 커밋·push 이후에만 반영 |
| **Git 원격** | — | ✅ **유일한 크로스 머신 동기화 경로**, 커밋에 반영된 것만 |

- Codex는 agentmemory MCP 도구뿐 아니라 **자체 네이티브 메모리(`~/.codex/memories_1.sqlite`)도 따로 갖고 있음** — 명시적으로 agentmemory를 쓰라고 하지 않으면 자기 메모리만 쓸 수 있으니, 중요 결정은 agentmemory에도 저장하도록 확인할 것.
- **설정 파일은 두 개다**: Claude는 `C:\Users\MONA\.claude\CLAUDE.md`, Codex는 `C:\Users\MONA\.codex\AGENTS.md`를 읽는다. 서로 다른 파일이라 한쪽에만 규칙을 적으면 다른 쪽은 모른다 — 공통 규칙은 **양쪽 파일에 각각** 적어야 한다.
- Git에 반영된 파일만 회사·집 공통 공유 정보로 간주한다. Git에 없는 로컬 변경은 다른 환경에서 보이지 않는다.

## 에이전트 간 직접 소통 (공유 메일함, 2026-08-21)
사용자가 "코덱스 결과, 클로드 결과를 내가 일일이 전달하는 게 불편하다"고 지적함 — 매번 한쪽 출력을 복사해 다른 쪽에 붙여넣는 대신, 두 에이전트가 이미 접속해 있는 **agentmemory MCP의 signal 도구를 작업 인계함으로 쓴다**.

- `memory_signal_send(from, to, content, type)` — 상대에게 메시지 전송. `type`은 info/request/response/alert/handoff 중 선택, `replyTo`로 스레드 연결 가능.
- `memory_signal_read(agentId, unreadOnly)` — 자기 앞으로 온 메시지 확인. 읽으면 delivered로 표시됨.
- 에이전트 ID는 `"claude"` / `"codex"`로 고정해서 서로 헷갈리지 않게 한다.
- 사용 시점: 협업 작업을 시작할 때 먼저 `memory_signal_read`로 상대가 남긴 미확인 메시지가 있는지 확인하고, 상대가 이어받아야 할 결과·피드백·수정 요청이 생기면 사용자를 거치지 말고 바로 `memory_signal_send`로 남긴다.
- 범위 제약: agentmemory는 PC별 로컬 서버이므로(위 표 참고) 이 메일함도 **같은 PC에서 두 에이전트가 함께 작업 중일 때만** 유효하다. 회사↔집처럼 PC가 다르면 이 방식으로는 전달되지 않고, 여전히 Git 커밋으로만 넘어간다.
- `CLAUDE.md`(Claude)와 `AGENTS.md`(Codex) 양쪽에 동일한 규칙을 각각 추가해 둠 — 한쪽 파일만 고치면 반쪽짜리 프로토콜이 된다.
- 완전 자동 루프(사용자 개입 없이 두 CLI가 무한히 주고받는 방식)는 검토 후 보류함 — 코드 수정이 사용자 승인 없이 왔다갔다 하는 위험, 중단 조건 설계 필요성 때문에 우선 "각자 턴에서 메일함을 확인/기록하는" 가벼운 프로토콜부터 시작하기로 함.

## 동시 편집 방지
한 파일을 두 에이전트가 동시에 수정하지 않는다. 다른 에이전트의 미커밋 변경이나 확인되지 않은 결과물을 임의로 덮어쓰지 않는다.

## 작업 인계 시 남겨야 할 내용
작업을 마치거나 다른 에이전트/환경으로 넘길 때 다음을 기록한다:
- 수행한 작업
- 변경 파일
- 검증 결과
- 미완료 사항
- 다음 담당 에이전트

## 신뢰 기준
- 중요한 변경은 **Git에 반영된 문서를 최종 기준**으로 삼는다.
- 사용자나 프로젝트의 최신 상태와 충돌하는 오래된 정보(agentmemory, Obsidian, 로컬 파일 어디서든)가 발견되면 자동으로 믿지 말고, 실제 코드·Git 상태·사용자의 최신 지시로 재확인한다.

## agentmemory 사용 범위
agentmemory의 일반적인 조회·기록은 사용자가 지속적으로 허용했다. 다만 삭제, 외부 공개, 강제 덮어쓰기 등 파괴적 작업은 사용자에게 별도 확인한다.
